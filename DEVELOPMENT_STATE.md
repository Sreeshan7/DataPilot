## Completed

### Phase 1 - Project Requirement Intelligence
Deterministic dictionary (148 concepts, 22 domains) reconciled with Gemini; provenance;
calibrated confidence with named, capped deductions.

### Phase 2 - Discovery and ranking (frozen except for the fixes listed below)
Kaggle (verified) + Gemini (AI-suggested) discovery, keywords-first query builder,
normalization with per-field provenance, deduplication, deterministic ten-factor ranker
(MATCH / UNKNOWN / MISMATCH, relevance 70 + trust 30, score == sum of contributions).

### Phase 2E - Offline evaluation
62-case / 173-candidate graded benchmark, golden set, ablation, sensitivity, controlled
stress probes, factor audit (`app/services/datasets/evaluation/`, `scripts/run_*.py`).

### Phase 3A - Dataset intelligence foundation
`DatasetIntelligence` per candidate (`schemas/intelligence.py`,
`services/datasets/intelligence.py`): evidence layers, schema state (VERIFIED / PARTIAL /
UNKNOWN), four-way target state, per-feature coverage, categorical compatibility, risks,
limitations, structured explanation. Verdicts are read from the ranker's output, never
re-decided. Trust rules are enforced by model validators, not only by convention.
Now returned inside every `/datasets/recommend` entry.

### Phase 3B - User A compatibility depth
- **Enrichment** (`DatasetDiscoveryService._enrich_top`, `KaggleDatasetSource.enrich`):
  the top-K (default 5) verified candidates are re-read from `/datasets/view/{ref}` and
  `/datasets/list/{ref}` (owner's full description, file names, extensions) and
  re-ranked. Two requests per candidate; failures keep the listing-level candidate.
- **Requirement coverage**: `FeatureCoverage.summary()` ("6 required: 4 matched,
  1 unknown, 1 missing", never "4/6") and a `requirement_coverage` section, one line per
  requirement.
- **Data type**: the project's stated modality against published file extensions and
  registry-stated modalities (a stated modality beats an extension: image datasets are
  stored as `.parquet`).
- **Temporal**: forecasting projects look for a time axis in the dataset's own text; only
  MATCH or UNKNOWN, never MISMATCH; absent when the project has no temporal requirement.
- `unknown_dimensions` lists only dimensions the project actually asked about.
- A feature absent from a **structured** schema is MISSING and blocks (LOW); one absent
  from a **prose** column list only keeps the dataset out of HIGH (prose lists are often
  partial).

### Phase 3C - User A recommendation quality
- **Hugging Face Hub** as a second verified registry (`huggingface_source.py`): declared
  `task_categories`, `format:`/`modality:` tags, license, and for ~1 dataset in 5 a
  structured `dataset_info.features` column list -> the only source of `SCHEMA_VERIFIED`.
- **Registry confirmation of AI suggestions**: up to 3 suggestions are looked up by name;
  only an identical name-token match promotes one to a registry record
  (`DatasetDeduplicator.absorb`).
- **Cross-source deduplication** (Kaggle + Hub verified in tests).
- **Recommendation confidence** (`build_confidence`): starts from compatibility, only ever
  capped, every cap reported.
- **Final recommendation** (`recommendation.py`): best match, <=3 alternatives each with
  its one most important trade-off, what is verified / unknown / missing, cautions, a
  deterministic summary, close-call flag. Never RECOMMENDS an unconfirmed AI suggestion or
  an incompatible dataset (enforced by the schema). Within a close call (<5.0 points) the
  more certain confirmed dataset wins.
- No LLM is used to write explanations: evidence -> structured explanation -> deterministic
  text. The structured explanation is shaped so an LLM could phrase it later without being
  asked what a dataset contains.

## Current Architecture

```
POST /api/v1/datasets/recommend
  ProjectAnalyzer (dictionary + Gemini, reconciled)
  -> build_dataset_search_query (project terms first, <=6)
  -> verified sources, queried once each:  Kaggle (+1 request if empty) | Hugging Face (<=2)
  -> Gemini suggestions (ai_suggested, unverified)
  -> normalize -> DatasetDeduplicator
  -> confirm up to 3 AI suggestions by exact name in the registries (absorb)
  -> DatasetRankingEngine.rank
  -> enrich top-5 verified (Kaggle view + file list) -> re-rank
  -> build_intelligence_report  (DatasetIntelligence per candidate)
  -> build_recommendations      (confidence per candidate + FinalRecommendation)
```

Trust rules, enforced in code:
- `AI_SUGGESTED` never becomes verified, never carries `SCHEMA_VERIFIED`, never says a
  feature is MISSING, is never RECOMMENDED (at most TENTATIVE), confidence <= LOW.
- AI claims about a merged registry record live in `ai_suggested_claims`, never in
  published fields.
- `SCHEMA_VERIFIED` / `SchemaState.VERIFIED` requires a *structured* column list published
  by a registry (`DatasetCandidate.columns`). It means "the registry's machine-generated
  schema", **not** "DataPilot parsed the file": no dataset file is ever downloaded.
- UNKNOWN is never MATCH and never MISSING; PRESENT/DERIVABLE/INCOMPATIBLE targets need
  declared evidence; a shared subject area alone is UNKNOWN.
- A dataset found incompatible is never put forward as the best match, however it ranks.

## Known Limitations

1. **The offline benchmark measures ranking only.** Intelligence, compatibility and the
   final recommendation are covered by unit tests and live invariants, not by a graded
   relevance benchmark. Whether the *recommended* dataset is the right one is not
   measured anywhere yet.
2. **Live results are not reproducible**: the analyzer (Gemini) changes queries run to run.
3. **Kaggle publishes no task types, no target description and no column schema** (0/20
   probed). Task is UNKNOWN for Kaggle, and Kaggle schema can never be VERIFIED.
4. **Prose is the only schema evidence for most datasets.** A prose column list can show a
   feature is present; a feature absent from it is reported MISSING with a "may be
   incomplete" note but cannot make a dataset LOW.
5. **Hugging Face search ANDs every word**, so it is queried with a 2-word then a 1-word
   head; recall for multi-concept projects is limited. ~18% of probed Hub datasets publish
   a column list, ~11% declare tasks.
6. **Title-level target matches**: a dataset whose *title* equals a dictionary synonym of
   the target (e.g. "Student Performance" for "final grade") can match the target at
   SEMANTIC quality. It is reported PRESENT but listed as *inferred*, capped at MEDIUM
   confidence, never as verified.
7. Raw-data risks (class imbalance, leakage, missingness, duplicates, identifier columns,
   small dataset) are **never emitted**: they need the file, which is Phase 4.
8. Data-type and temporal checks use published file extensions / registry modality labels /
   keyword evidence in the dataset's own text. They do not inspect data.
9. Phase 1 gaps carried over: dictionary `dataset_requirements` are not merged into the
   output; `conflicts` is always empty; `llm_request_timeout` / `llm_max_retries` are not
   used by `generate_content`.
10. `task_match` + `compatibility` double-charge a wrong declared task (documented in the
    stress report, left as a decision).
11. The Postman collection still covers only the Phase 1 analyzer.
12. Windows consoles: any script that prints dataset titles must be encoding-safe (fixed in
    `run_e2e.py`). `run_evaluation.py` and `run_stress.py` were not audited for this.

## Known Intentional Failures

Two golden expectations in the offline benchmark are deliberately unmet
(`KNOWN_FAILURES` in `app/services/datasets/evaluation/golden_set.py`;
`test_known_failures_are_actually_failing`
fails if one silently starts passing):

1. `health-target-conflict` - a dataset declaring a *readmission* outcome ranks first for a
   project needing *mortality*. **Expected:** the mortality project rejects it. **Current:**
   ranks first. **Why:** the dictionary has no label space for "mortality", so the project
   side resolves to nothing and contradiction detection (deliberately silent when either
   side is unknown) never compares the two. **Fix:** dictionary coverage, not ranking.
2. `health-readmission-sparse` - a generic notes collection can outrank the real encounter
   extract. **Why:** the right dataset publishes only prose (UNKNOWN, earns nothing) while
   the wrong one declares a task type and is credited. **Fix:** richer evidence for the
   right dataset, not a ranking change.
